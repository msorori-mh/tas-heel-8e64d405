# الخطة قوية، وأعتمد الانتقال إلى المرحلة 03، لكن قبل التنفيذ أريد **6 تصحيحات إلزامية** حتى لا ندخل أخطاء تشغيلية في أول Migration حقيقي.

```text
IMPORT_STAGING_AND_EXECUTION_IMPLEMENTATION_03
= GO_WITH_REQUIRED_CORRECTIONS

MIGRATION_FILE_CREATION = ALLOWED
MIGRATION_APPLY = FORBIDDEN
PRODUCTION_WRITE = FORBIDDEN
PUBLISH = FORBIDDEN

```

1. **لا تجعل** `dry-run` **نفسه يكتب Staging.** سبق أن ثبتنا الفرق بينهما، ويجب الحفاظ عليه:
  ```text
  dry-run / validate = ZERO DB writes
  prepare / stage    = import_jobs + staging writes
  execute            = domain writes

  ```
  يمكن للواجهة تنفيذ `validate → prepare` متتابعين، لكن لا نسمي عملية تكتب DB باسم Dry-run.
2. **لا تسمح لـFull Admin بالكتابة المباشرة إلى جداول Staging/Review من PostgREST.** الأفضل:
  ```text
  authenticated users → SELECT حسب RLS فقط
  application writes → RPC / trusted server only
  service_role → backend operational access

  ```
  وRPC الـ`SECURITY DEFINER` يجب أن يحتوي:
  ```sql
  SET search_path = public

  ```
  مع `REVOKE EXECUTE ... FROM PUBLIC, anon` ومنح التنفيذ للأدوار المطلوبة فقط.
3. **التنفيذ الذري يجب أن يكون داخل قاعدة البيانات، لا من TypeScript عبر عدة استدعاءات.** عبارة:
  > معاملة واحدة لكل قالب  
  > لا تتحقق إذا نفذ Server Function عدة عمليات Supabase متفرقة. المطلوب:
  ```text
  executeContentImport()
       ↓
  RPC واحدة للقالب
       ↓
  BEGIN transaction implicit in function call
       ↓
  revalidate + lock + plan + domain writes + counters
       ↓
  success OR complete rollback

  ```
4. **أضف حماية Concurrency.** الـIdempotency وحدها لا تكفي إذا نفذ مشرفان نفس Job في اللحظة نفسها. داخل RPC:
  ```text
  SELECT import_job ... FOR UPDATE

  ```
  مع رفض:
  ```text
  already applying
  already applied
  invalid status transition

  ```
  وفهارس UNIQUE مناسبة على Staging بحيث لا يمكن لنفس:
  ```text
  job_id + template_key + natural_key

  ```
  الظهور مرتين دون كشف صريح.
5. `content_review_state` **يجب ألا يقبل الكتابة المباشرة إطلاقاً.** بعد بناء RPC المراجعة:
  ```text
  approve
  reject
  publish لاحقاً

  ```
  لا تمنح `UPDATE` مباشر للمستخدمين حتى لو كانوا Admin؛ لأن direct update قد يتجاوز منطق `content_hash` وإعادة التصفير.
6. **القالب 09 الخاص بالأسئلة يحتاج Contract تنفيذي صريح، وليس مجرد عبارة "يوجّه إلى QB workflow".** قبل PASS للمرحلة يجب أن يثبت الاختبار أن:
  ```text
  template 09
     ↓
  approved QB import/runtime API
     ↓
  revision / validation / answer protection

  ```
  ولا يوجد في أي مكان:
  ```text
  generic upsert into questions

  ```
  والأهم: إذا كان Question Bank workflow لا يمكن إدخاله في نفس transaction، يجب توثيق Boundary واضحة وعدم ادعاء atomicity مشتركة مع بقية القوالب.

### إغلاق المرجع متعدد الأشكال (S4 — MEDIUM) بطريقة fail-closed

- trigger تحقق وجود على `(entity_type, entity_id)` يرفض أي صف لا يقابله كيان فعلي داخل الـ allowlist (بحث مباشر لكل نوع، بدون SQL ديناميكي).
- تنظيف تلقائي: triggers حذف على كل جدول كيان تُزيل صف المراجعة المقابل، فلا تبقى حالة يتيمة.
- مسار الكتابة الوحيد المسموح من التطبيق هو RPC بـ SECURITY DEFINER يعيد فحص الدور.

### S3 (MEDIUM) و S5 (LOW)

- S3: عزل ملكية Staging منقول حرفياً إلى الـ Migration ومغطّى باختبار.
- S5: كل trigger أمني يخرج مُفعّلاً؛ اختبار ثابت (static test) يفشل إذا وُجد `-- CREATE TRIGGER` معلّق داخل مجلد `supabase/migrations`.

## 3. محرّك التنفيذ `executeContentImport`

آلة الحالة: `validated → planned → applying → applied | failed` (وفق `EXECUTION_TRANSITIONS` الموجودة).

- معاملة واحدة لكل قالب؛ فشل صف واحد يُرجع القالب بالكامل (rollback) ويوقف القوالب اللاحقة.
- إعادة تحقق إلزامية داخل المعاملة (نتائج dry-run غير موثوقة).
- `BLOCKED_PUBLISHED` يُفحص **قبل** أي Domain Write ولا يُطبَّق أبداً.
- Idempotency: نفس المفتاح + نفس الهاش → `skipped`؛ مسودة متغيّرة → `UPDATE_DRAFT`/`NEW_REVISION`؛ محتوى منشور متغيّر → `BLOCKED_PUBLISHED`.
- الأسئلة لا تمر عبر generic upsert — تُوجَّه إلى Question Bank workflow المعتمد.
