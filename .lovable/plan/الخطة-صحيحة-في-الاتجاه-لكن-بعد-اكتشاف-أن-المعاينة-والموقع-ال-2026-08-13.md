# الخطة صحيحة في الاتجاه، لكن بعد اكتشاف أن **المعاينة والموقع المنشور يستخدمان قاعدة Lovable Cloud واحدة** فهناك قرار حوكمة مهم يجب تثبيته الآن:

```text
PRODUCTION_CONTENT_IMPORT_READINESS_REVIEW_10
= GO_WITH_REQUIRED_CORRECTIONS

DATABASE_CLASSIFICATION = SHARED_PRODUCTION_DATASTORE
STAGE_10_DB_WRITES = FORBIDDEN
STAGE_10_MIGRATIONS = FORBIDDEN
CONTENT_PUBLISH = FORBIDDEN

```

أهم أثر لهذا الاكتشاف: أي كتابة مستقبلية، حتى لو تمت من واجهة المعاينة وبمحتوى `draft`، هي **كتابة على قاعدة الإنتاج فعلياً**. لذلك نتوقف عن وصف التشغيل القادم بأنه Non-Prod.

### أوافق على معظم الخطة، مع 4 تعديلات مهمة

**1. خطة Rollback لا تعتمد على الحذف العكسي فقط.**  
الحذف بأكواد الدفعة مناسب للإدراجات الجديدة، لكنه لا يعيد الحالة السابقة عند `UPDATE_DRAFT` أو تغيير Targets/Review State. قبل كل دفعة حقيقية يجب أخذ Logical Snapshot للصفوف المتأثرة، إضافة إلى baseline counts، بحيث نستطيع إعادة **القيم السابقة** وليس مجرد حذف الجديد.

**2. أول Batch بدون أسئلة قرار صحيح جداً.**  
أعتمد أن أول كتابة حقيقية تكون صغيرة:

```text
مادة واحدة
→ وحدة
→ درس
→ محتوى/شرح
→ موارد
→ تقييم

NO QUESTIONS
NO PUBLISH

```

ثم نتحقق من Admin + Student visibility قبل السماح بأي Batch أوسع.

**3. قرار G-1 الأساسي صحيح: لا نعيد Legacy identity إلى** `questions`**.**

أعتمد الاتجاه:

```text
assessment_questions
        ↓
published question only
        ↓
question_targets

```

ولا نعتمد `subject_id/lesson_id` القديمين في جذر السؤال كمصدر حقيقة.

لكن توجد نقطة حرجة يجب إضافتها إلى التصميم: **الـTarget يجب أن يكون مرتبطاً بالـRevision أو بالنسخة المنشورة بصورة يمكن إثباتها**.

لأن القالب 09 يستطيع إضافة Target أثناء وجود Draft. وإذا كان لدينا سؤال منشور قديم ثم استوردنا Draft جديداً بوجهة جديدة، فلا يجوز أن يصبح Target الجديد صالحاً فوراً للتقييم لمجرد أن:

```text
question.current_published_revision_id IS NOT NULL

```

بينما الـTarget جاء من Draft غير منشور.

العقد الصحيح يجب أن يضمن أحد النموذجين:

```text
question_targets.revision_id

```

ويتحقق الرابط من:

```text
target.revision_id = question.current_published_revision_id

```

**أو** توجد مرحلة promotion/activation عند `publish_question_revision` تجعل Targets الخاصة بالنسخة المنشورة وحدها Active.

بدون ذلك، G-1 لا يعتبر مغلقاً أمنياً ووظيفياً.

**4. لا نعتبر migrations 03–09 "جاهزة للإنتاج" لأنها مطبقة بالفعل.**  
الصياغة الأدق:

```text
SCHEMA_ALREADY_PRESENT_ON_SHARED_PRODUCTION_DB

```

والمرحلة 10 توثق ما حدث وتفحص أثره، لكنها لا تعيد تطبيق أو نقل أي Migration.

### قرار G-1 الذي أعتمده تصميمياً

```text
G-1 ARCHITECTURE = TARGETS-BASED
LEGACY ROOT BINDING = REJECTED

```

مع القواعد:

```text
Draft question
→ cannot bind to assessment

Published question
→ may bind only through target
   belonging to the current published revision

Draft/new-revision targets
→ cannot influence assessment binding

publish_question_revision
→ activates/promotes the revision's targets atomically

assessment link validation
→ published revision + active target match

student answer protections
→ unchanged

```

وهذا يصبح أساس المرحلة 11.

نغلق فيها G-1 بالكود والاختبارات أولاً، **قبل إدخال الأسئلة والتقييمات المرتبطة بها إلى الاستخدام الحقيقي**.

النقطة الأهم التي كشفناها الآن: **قاعدة البيانات نفسها Production بالفعل؛ ما بقي قبل أول رفع حقيقي هو حماية عملية الكتابة، وليس "نقل النظام إلى Production".**PRODUCTION_CONTENT_IMPORT_READINESS_REVIEW_10

مرحلة مراجعة وجاهزية + قرار معماري لـ G-1. لا استيراد إنتاجي فعلي ولا نشر محتوى في هذه المرحلة.

## حقيقة أساسية يجب تثبيتها أولاً

فحص قاعدة البيانات الحالية أظهر:

- لا توجد قاعدتان (Non-Prod / Prod) منفصلتان. المشروع يعمل على قاعدة Lovable Cloud واحدة تخدم المعاينة والموقع المنشور معاً.
- كل migrations المراحل 03–09 **مطبقة بالفعل** على هذه القاعدة الواحدة، و`supabase/migrations-pending/` فارغة عملياً.
- بقايا الـ e2e: `subjects/questions_revisions/question_targets/assessment_questions` بأكواد `e2e-*` = **صفر**، بينما `import_jobs` = 29 صف (سجل تدقيق محفوظ كما هو مطلوب).
- `question_revisions` = 0، `published` = 0، أي لا يوجد أي محتوى بنك أسئلة حقيقي بعد.

النتيجة: «نقل migrations إلى الإنتاج» ليس بنداً قابلاً للتنفيذ هنا. البند الحقيقي هو: **أول كتابة محتوى حقيقي تتم على نفس القاعدة التي يراها الطلاب**، ولذلك تتحول المرحلة 10 من «مقارنة بيئتين» إلى «ضوابط كتابة آمنة على بيئة واحدة».

## ما تنفذه المرحلة 10

### 1. تقرير الجاهزية `docs/import/PRODUCTION-CONTENT-IMPORT-READINESS-REVIEW-10.md`

- جرد كامل للـ migrations المطبقة الخاصة بالاستيراد وبنك الأسئلة مع حالة كل منها.
- إثبات موثق بالاستعلامات لخلو القاعدة من بيانات `e2e-*` مع بقاء `import_jobs`.
- Baseline snapshot لأعداد الصفوف في جداول المحتوى قبل أول دفعة.
- خطة Backup/Rollback: نقطة استرجاع قبل كل دفعة، وrollback على مستوى القالب اعتماداً على ذرّية per-template + `import_jobs.id` كمفتاح تتبع، وقائمة استعلامات حذف عكسي بأكواد الدفعة.
- حدود الدفعات: حد أقصى للصفوف لكل قالب، ومنع تشغيل دفعتين متزامنتين، ومراقبة `import_jobs` (jobs عالقة، jobs فاشلة، معدل الأخطاء).
- صلاحيات المشغلين: من يملك `admin` / `content_manager` / capability النشر، ومن يُسمح له فعلياً بتشغيل prepare/execute.

### 2. Checklist أول دفعة حقيقية

`docs/import/FIRST-PRODUCTION-BATCH-CHECKLIST-10.md`: مادة واحدة → وحدة → درس → موارد → تقييم، بدون أسئلة، مع تحقق طالب حقيقي بعد الدفعة. لا تُنفذ الدفعة في هذه المرحلة؛ تبقى بانتظار تفويض مكتوب.

### 3. قرار G-1 (المخرج الأهم)

الوضع المؤكد بالكود: `qb_import_ingest_revision` ينشئ جذر السؤال كـ identity shell بلا `lesson_id/subject_id`، و`qb_sync_question_legacy` ما زالت stub، وtrigger التحقق يرفض الربط لأنه يقرأ الربط legacy من جذر السؤال.

الخيار الموصى به: **الربط عبر `question_targets` وقت النشر، لا عبر جذر السؤال**.

```text
draft revision → publish_question_revision → question_targets (subject/lesson)
                                                    ↓
                        validate_assessment_question_link يقرأ targets
                                                    ↓
                        assessment_questions binding مسموح للمنشور فقط
```

قواعد ملزمة للقرار:

- لا كتابة أي أعمدة legacy في `public.questions` كشرط للربط.
- الربط مسموح فقط لسؤال له `current_published_revision_id` غير فارغ.
- التحقق يطابق مادة/درس التقييم مع `question_targets` وليس مع جذر السؤال.
- المسودات تبقى غير مرئية للطالب، وحماية الإجابات كما هي.

الخيار البديل الموثق للرفض: تعبئة legacy عند النشر (أبسط لكنه يعيد ازدواج الهوية ويخالف نموذج revisions/targets).

المرحلة 10 تنتج القرار والتصميم والاختبارات المطلوبة لإغلاقه؛ التنفيذ الفعلي (migration + E2E) يصبح المرحلة 11 بعد اعتمادك.
