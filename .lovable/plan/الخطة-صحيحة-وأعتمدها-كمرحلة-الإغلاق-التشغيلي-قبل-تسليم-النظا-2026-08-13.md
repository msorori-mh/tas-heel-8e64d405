# الخطة صحيحة، وأعتمدها كمرحلة الإغلاق التشغيلي قبل تسليم النظام ليوسف، مع **5 ضوابط إلزامية** حتى لا نغلقها شكلياً فقط:

```text
CURRICULUM_CONTENT_ENTRY_READINESS_13
= GO_WITH_REQUIRED_GUARDS

CURRICULUM DATA WRITES = NO
PRODUCTION CONTENT INSERT = NO
NEW MIGRATION = NOT EXPECTED

```

### 1. إغلاق `SUBJECT_AS_BRANCH` تشغيلياً بالكامل

أوافق على إضافة:

```text
group_code
group_name

```

إلى عقد Template 01 + القالب + CRUD.

لكن قاعدة التعديل تكون:

```text
subject_code:
- set once on create
- immutable afterwards

group_code:
- set on create
- إذا كان NULL يجوز تعيينه لاحقاً فقط قبل وجود محتوى/اعتماد/نشاط
- بعد استخدام المادة فعلياً يصبح immutable

group_name:
- editable display label

```

ويضاف Validate:

```text
same grade
+ same curriculum_track
+ same group_code
⇒ same group_name

```

مع حارس يؤكد أن `group_code` **لا يدخل في RLS أو can_access_subject أو question_targets**.

### 2. إغلاق مسارات الحذف القديمة إلزامي

هذه نقطة مانعة:

```text
SubjectDeleteDialog
UnitDeleteDialog
LessonDeleteDialog

```

يجب ألا يبقى فيها أي:

```text
.from(...).delete()

```

المسار الوحيد:

```text
preview RPC
↓
عرض الأثر والموانع
↓
Full Admin فقط
↓
admin_curriculum_delete
↓
audit log

```

و`content_manager`:

```text
Preview       ✅
Hard Delete   ❌

```

حتى لو ظهر الحوار له.

وأريد اختباراً ثابتاً يبحث في كود Admin ويثبت:

```text
direct curriculum PostgREST DELETE paths = 0

```

### 3. صلاحية يوسف تحتاج صياغة دقيقة

لا نكتب فقط:

```text
content_manager يكفي

```

بل نفصل:

```text
content_manager:
01–07 create/edit/import       ✅
Validate / Prepare / Execute   ✅
09 question draft import       ✅
Hard delete                    ❌
User/security administration   ❌
QB publish                     ❌ unless separate capability
Content publish                ❌ unless separate publisher capability

```

وهذا مهم جداً لأن ترتيب العمل الكامل هو:

```text
يوسف:
01→07→09

ثم Reviewer:
Review

ثم Publisher/QB Publisher:
Publish

ثم يوسف/المشغل:
08 binding

```

إذن يمكن أن يكون:

```text
CONTENT_ENTRY_OPERATOR_READY = YES

```

حتى لو كان النشر يحتاج شخصاً/صلاحية منفصلة.

### نقطة أخيرة مهمة

بما أن قاعدة المنهج أصبحت نظيفة، **لا نحتاج إنشاء أي بيانات لاختبار هذه المرحلة**. الاختبارات التي تحتاج بيانات تستخدم fixtures/isolated PG أو mocks؛ لا نعيد تلويث القاعدة المشتركة.

## بوابة الإغلاق

أعتمد الحكم النهائي فقط إذا خرج:

```text
SUBJECT_AS_BRANCH OPERATIONAL          PASS
SAFE ADMIN CRUD                        PASS
DIRECT DELETE BYPASS                   ZERO
CONTENT_MANAGER MATRIX                 VERIFIED
OFFICIAL 01–09 TEMPLATES               PASS
DATA DICTIONARY                        COMPLETE
NAMING CONVENTION                      COMPLETE
OPERATOR GUIDE                         COMPLETE
IMPORT CENTER LEGACY UX                CLOSED
TEMPLATE ORDER                         SINGLE SOURCE
TESTS                                  PASS
TYPECHECK                              PASS
BUILD                                  PASS
CURRICULUM DB WRITES DURING STAGE 13   ZERO

= CONTENT_ENTRY_OPERATOR_READY = YES

```

بعد ذلك **نتوقف عن تطوير بنية الاستيراد** ونعتبر النظام جاهزاً لتسليمه ليوسف؛ وعندما يصبح المحتوى متوفراً يبدأ مباشرة من Template 01 دون الحاجة للعودة إلينا لاتخاذ قرارات بنيوية جديدة.CURRICULUM_CONTENT_ENTRY_READINESS_13

إغلاق تشغيلي قبل تسليم النظام لموظف المحتوى (يوسف). **لن تُكتب أي بيانات منهج في قاعدة البيانات** — مراجعة، إصلاح واجهات، وتوثيق فقط.

## ما تم التحقق منه فعلياً الآن

- أعمدة `group_code` و `group_name` **موجودة في جدول subjects** (DB ✅).
- لكنها **غير موجودة** في عقد الاستيراد `src/lib/import/import-contract.ts` ولا في قالب 01 ولا في نافذة إضافة/تعديل المادة → قرار SUBJECT_AS_BRANCH **غير مطبق تشغيلياً**.
- الحذف الصلب ما زال مباشراً عبر PostgREST في: `SubjectDeleteDialog.tsx`، `UnitDeleteDialog.tsx`، `LessonDeleteDialog.tsx` (`.from(...).delete()`) — مسار حذف ثانٍ غير محمي بجانب `admin_curriculum_delete`.
- ما زال في `/admin/import` قسم أزرار معطلة بشارة «قريباً».

## نطاق العمل

### 1. إغلاق SUBJECT_AS_BRANCH

- إضافة `group_code` (اختياري) و `group_name` (اختياري) إلى عقد قالب 01 وإعادة توليد القالب.
- تحديث `SubjectEditDialog`: عند الإنشاء `subject_code` إلزامي + حقول التجميع؛ عند التعديل `subject_code` و `group_code` للقراءة فقط، `name` و `group_name` قابلان للتعديل.

### 2. توحيد مسار الحذف

- تحويل حوارات حذف المادة/الوحدة/الدرس لاستخدام `admin_curriculum_delete_preview` + `admin_curriculum_delete` فقط، وإزالة أي `.delete()` مباشر من واجهة الإدارة.

### 3. تنظيف مركز الاستيراد `/admin/import`

- حذف قسم «قريباً» وأي بقايا POC المحافظات.
- اشتقاق ترتيب قائمة نوع القالب من `IMPORT_EXECUTION_ORDER` (01→02→…→07→09→08).
- تصحيح صياغة التسلسل: «07 إنشاء التقييم ← 09 استيراد الأسئلة كمسودات ← مراجعة ← نشر ← 08 الربط».
- تحسين جدول سجل العمليات بأعمدة مسماة: Rows / Inserted / Updated / Skipped / Blocked / Errors / Status، وإزالة عبارة «تفاصيل الأخطاء لاحقاً».
- زر تنزيل حزمة القوالب الرسمية التسعة كاملة + رابط دليل التعبئة.

### 4. التوثيق

- `docs/import/NAMING-CONVENTION.md`: اتفاقية رسمية لأكواد subject/unit/lesson/explanation/resource/assessment/question.
- `docs/import/DATA-DICTIONARY-AR.md`: قاموس عربي لكل عمود في القوالب 01–09 (إلزامي/اختياري، النوع، المرجع، مثال).
- `docs/import/CONTENT-OPERATOR-GUIDE-AR.md`: دليل مختصر لموظف المحتوى بترتيب العمل والبوابات.

### 5. التحقق النهائي

- مراجعة القوالب 01–09 حرفياً مقابل العقد (اختبارات القوالب الحالية).
- تأكيد أن دور `content_manager` يكفي للإدخال دون Full Admin (قراءة سياسات RLS والدوال).
- تأكيد دعم الهرم Subject→Unit→Lesson و Subject→Lesson (درس بلا وحدة).
- تشغيل الاختبارات + typecheck، وإخراج التقرير النهائي `docs/import/CURRICULUM-CONTENT-ENTRY-READINESS-13.md` مع الحكم `CONTENT_ENTRY_OPERATOR_READY = YES/NO` وقائمة الموانع المتبقية إن وُجدت.

## ملاحظات تقنية

- لا Migration جديدة متوقعة إلا إذا لزم تعديل دالة `admin_curriculum_delete` لدعم الحذف من الحوارات؛ في تلك الحالة تُعرض للموافقة قبل التطبيق.
- لا `INSERT` على أي جدول منهج.
