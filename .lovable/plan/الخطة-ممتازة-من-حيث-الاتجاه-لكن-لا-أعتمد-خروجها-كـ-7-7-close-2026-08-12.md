# الخطة **ممتازة من حيث الاتجاه، لكن لا أعتمد خروجها كـ** `7/7 CLOSED` **بهذه الصيغة بعد**. القرار:

```text
IMPORT_EXECUTION_READINESS_GAP_CLOSURE_02
= GO_WITH_REQUIRED_REVISIONS

PRODUCTION_WRITE = NO
MIGRATION_APPLY = NO
EXECUTE_ENABLE = NO
PUBLISH = NO

```

هناك **5 تعديلات إلزامية قبل الإغلاق النهائي**:

1. **لا تستخدم** `(lesson_id, sort_order)` **كمفتاح طبيعي** لـ`lesson_explanations` و`lesson_resources`.  
`sort_order` ترتيب قابل للتغيير وليس هوية؛ تغيير ترتيب موردين قد يجعل النظام يفسرهما كتحديثات على كيانين مختلفين. الأفضل إضافة هوية استيراد مستقرة:
  ```text
  explanation_code
  resource_code

  ```
  والنطاق:
  ```text
  (lesson_id, explanation_code)
  (lesson_id, resource_code)

  ```
  ويبقى `sort_order` مجرد خاصية قابلة للتحديث.
2. `content_review_state` **لا يكفي أن يكون** `(entity_type, entity_id)` **فقط.**  
أخطر مشكلة: إذا تمت الموافقة على المحتوى ثم تغير الـpayload، قد تبقى حالة `approved` مرتبطة بالكيان نفسه. يجب ربط المراجعة بالإصدار/البصمة:
  ```text
  entity_type
  entity_id
  content_hash / revision
  review_status
  publication_status
  reviewed_by
  reviewed_at
  rejection_reason

  ```
  وأي تغير في `content_hash` يعيد المحتوى إلى:
  ```text
  pending + draft

  ```
3. `lesson_assessments.code` **يجب تحديد نطاق تفرده صراحة.**  
لا نكتب فقط "unique partial index". يجب أن يقرر العقد هل:
  ```text
  UNIQUE(code)

  ```
  أم:
  ```text
  UNIQUE(lesson_id, code)

  ```
  والأفضل أن يتبع **النطاق الحقيقي الذي أثبته Schema Audit**، لا افتراضاً جديداً.
4. `deriveSubjectSlug(subjectCode)` **يجب أن يكون collision-safe.**  
التطبيع وحده قد يحول كودين مختلفين إلى slug واحد. يجب أن يكون العقد حتمياً **وفريداً**؛ مثلاً normalization مقيد إذا كان `subject_code` نفسه له charset مضمون، أو suffix hash حتمي عند الحاجة. أضيفوا اختباراً مثل:
  ```text
  different subject codes
  must never silently derive the same slug

  ```
5. آلة حالات Execute تحتاج حالة فشل صريحة. بدلاً من:
  ```text
  parsed → validated → planned → applied|blocked

  ```
  أعتمد:
  ```text
  parsed
     ↓
  validated | blocked
     ↓
  planned
     ↓
  applying
     ↓
  applied | failed

  ```
  مع تثبيت أن:
  ```text
  blocked = لم تبدأ domain writes
  failed  = بدأت محاولة التنفيذ وفشلت

  ```
  وأن التنفيذ المستقبلي يجب أن يحدد Atomicity/rollback بوضوح قبل Migration.

أما بقية القرارات فأوافق عليها:

- `resource_url` مطلوب طالما DB الحالية `NOT NULL`.
- `metadata jsonb` مناسب للقالب 06، **بشرط allowlist واضحة للحقول السبعة** وعدم جعله مخزناً عاماً لأي بيانات.
- إضافة `subject_code` إلى 04–07 صحيحة إذا أثبت العقد أن `(subject_code, lesson_code)` يزيل الالتباس.
- `ROW_HASH_FIELDS` ممتازة ويجب أن تكون canonical وليست hash لـJSON غير مستقر.
- `BLOCKED_PUBLISHED` يبقى invariant لا يمكن تجاوزه.
- Question Bank workflow يبقى منفصلاً ولا يقوم Generic Import بالكتابة المباشرة على الأسئلة المنشورة.
- ملف:
  ```text
  IMPORT-EXECUTION-READINESS-02.NOT_APPLIED.sql

  ```
  مناسب للمراجعة فقط ولا يدخل `supabase/migrations`.

### بوابة الخروج المعدلة

```text
7/7 design gaps CLOSED
+ stable natural identities (not sort_order)
+ review bound to content revision/hash
+ collision-safe subject slug
+ explicit assessment-code uniqueness scope
+ execute failure/atomicity contract
+ BLOCKED_PUBLISHED invariant
+ Question Bank workflow unchanged
+ bun run test:import-contract PASS
+ no CRITICAL/HIGH security findings
= READY_FOR_MIGRATION_REVIEW

```

بعد هذه التعديلات، إذا خرجت المرحلة `PASS`، **لا نذهب مباشرة للإنتاج**؛ نفتح فقط المرحلة التالية:

```text
IMPORT_STAGING_AND_EXECUTION_IMPLEMENTATION_03

```

وفيها يجوز **إنشاء Migration داخل الكود ومراجعتها واختبارها محلياً، لكن لا تطبيقها على Production إلا بأمر صريح منك**.

هذه هي الآن الأولوية الأولى للمشروع، وأكاديمية معلم الثانوية تبقى متوقفة.IMPORT_EXECUTION_READINESS_GAP_CLOSURE_02

مرحلة **غير إنتاجية**: لا Migration، لا كتابة في قاعدة البيانات، لا Publish. الهدف إغلاق الفجوات السبع تصميمياً وتوثيقياً وباختبارات حارسة، بحيث يصبح فتح Migration لاحقاً خطوة تنفيذ فقط بلا قرارات مفتوحة.

  - رسم التبعية ما زال مطابقاً للـ FKs الفعلية.
