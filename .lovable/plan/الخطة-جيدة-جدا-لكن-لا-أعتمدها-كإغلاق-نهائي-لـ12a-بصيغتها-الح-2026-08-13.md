# الخطة جيدة جداً، لكن **لا أعتمدها كإغلاق نهائي لـ12A بصيغتها الحالية** لسبب واحد مهم: هي لا تُدخل قرار **المواد ذات الفروع المتعددة** الذي اكتشفناه قبل قليل.

القرار:

```text
CONTENT_IMPORT_TEMPLATE_CONTRACT_SYNC_12A
= GO_WITH_BRANCH_ARCHITECTURE_GATE

FIRST_REAL_CONTENT_BATCH_12
= HOLD

```

ما يمكن تنفيذه الآن بأمان من 12A:

- توحيد `DRY_RUN_CONFIG` مع `IMPORT_ENTITY_CONTRACTS`.
- تصحيح `subject_code / explanation_code / resource_code / resource_url`.
- إزالة ازدواج القوالب القديمة من واجهة الأدمن.
- توحيد ترتيب العرض مع `IMPORT_EXECUTION_ORDER`.
- تحديث `planned_unique → db_unique` بعد التحقق الفعلي.
- تحديث الاختبارات وTypecheck/Build.

لكن **لا أريد اعتماد ملفات Excel 01–09 كنسخة نهائية طويلة الأجل قبل حسم Subject Branches**؛ لأن القرار قد يضيف `branch_code` إلى بعض القوالب ويغير Dependency Graph.

المرحلة المطلوبة بالتوازي هي:

```text
MULTI_BRANCH_SUBJECT_ARCHITECTURE_REVIEW_12B

```

وتراجع تحديداً:

```text
Subject
├─ Branch (optional)
│  ├─ Unit (optional)
│  │  └─ Lesson
│  └─ Lesson
├─ Unit
│  └─ Lesson
└─ Lesson

```

ويجب على Lovable فحص المواد الحقيقية المتفرعة، خصوصاً العربية والتربية الإسلامية، وتحديد هل:

```text
A) branch = unit

```

كافٍ فعلاً لكل المناهج،

أم نحتاج:

```text
B) subject_branches

```

كطبقة مستقلة.

### توجيهي المعماري

لا أوصي باستخدام `units` كبديل عام للفرع إلا إذا أثبت Audit أن **الفرع لا يحتوي وحدات في أي منهج مستهدف**. إذا كان لدينا مثلاً:

```text
اللغة العربية
→ النحو
   → الوحدة الأولى
   → الوحدة الثانية

```

فلا يمكن أن يكون «النحو» Unit، وإلا فقدنا مستوى هيكلياً.

لذلك يجب أن يخرج 12B بقرار واضح عن:

- هل نحتاج `subject_branches`.
- هل `branch_code` اختياري أم مطلوب لبعض القوالب.
- أثره على `units`.
- أثره على `lessons`.
- أثره على 04–07.
- أثره على `questions/question_targets`.
- أثره على Assessment binding.
- Dependency Graph الجديد.
- هل نضيف قالباً مثل:
  ```text
  01B_subject_branches

  ```
  أم لا.

### نقطة مهمة في تصميم Single Source

فكرة:

```text
requiredColumns / knownColumns
← IMPORT_ENTITY_CONTRACTS.fields

```

ممتازة، لكن لا تجعلها مجرد استخراج آلي لكل حقول DB. يجب أن يحتوي العقد نفسه على تمييز مثل:

```text
templateField: true
requiredInTemplate: true/false

```

لأن بعض الحقول قد تكون داخلية/مشتقة ولا ينبغي ظهورها في Excel.

### الترتيب التنفيذي الذي نعتمده حالياً

للمواد غير المتفرعة:

```text
01 subjects
→ 02 units
→ 03 lessons
→ 04 book_contents
→ 05 explanations
→ 06 resources
→ 07 assessments
→ 09 questions
→ Review/Publish
→ 08 assessment_questions

```

لكن إذا ثبتت طبقة Branch فسيصبح مثلاً:

```text
01 subjects
→ 01B subject_branches
→ 02 units
→ 03 lessons
→ ...

```

مع بقاء Branch اختيارياً للمواد التي لا تحتاجه.

## بوابة الخروج المعدلة

لا نعلن:

```text
OFFICIAL XLSX FINAL

```

إلا عندما يتحقق:

```text
TEMPLATE CONTRACT PARITY             PASS
DRY-RUN / EXECUTE PARITY             PASS
LEGACY TEMPLATE CONFUSION            CLOSED
CANONICAL ORDER                      SINGLE SOURCE
DB CONSTRAINT STATUS                 CURRENT
MULTI-BRANCH ARCHITECTURE            DECIDED
BRANCH IMPACT ON 01–09               RESOLVED
OFFICIAL XLSX REGENERATED AFTER THAT PASS
TESTS / TYPECHECK / BUILD             PASS

```

**الخلاصة:** نفّذوا تصحيحات 12A الآن، لكن اجعلوا إعادة توليد واعتماد القوالب الرسمية النهائية بعد مراجعة 12B مباشرة. بهذه الطريقة لا نصلح القوالب اليوم ثم نعيد تغييرها غداً عند إضافة فروع المواد.  راجع بنية المناهج الحالية وقوالب الاستيراد مع التركيز على **المواد ذات الفروع المتعددة** مثل اللغة العربية والتربية الإسلامية وأي مواد مشابهة.

لا تنفذ Migration أو كتابة قاعدة بيانات.

المطلوب:

1. افحص الجداول الحالية `subjects / units / lessons` والعلاقات الموجودة بينها.
2. حدد هل يوجد في الـSchema الحالي مفهوم فعلي يمكن أن يمثل `Subject Branch` دون إساءة استخدام `units`.
3. افحص ملفات المحتوى والقوالب المتاحة وحدد أمثلة فعلية للمواد المتفرعة، ولا تفترض أسماء الفروع من عندك.
4. قارن بين خيارين:
  - تمثيل الفرع كـUnit.
  - إنشاء طبقة `subject_branches`.
5. اختبر الحالات:
  - مادة بلا فروع.
  - مادة بفروع ولكل فرع وحدات.
  - مادة بفروع ودروس مباشرة.
  - درس مباشر تحت المادة بدون وحدة.
6. حدد أثر ذلك على قوالب 01–09، خصوصاً `units / lessons / contents / assessments / questions / question_targets`.
7. اقترح Dependency Graph محدثاً.
8. حدد هل نحتاج قالباً جديداً مثل `01B_subject_branches`.
9. أعط قراراً معمارياً نهائياً قبل `FIRST_REAL_CONTENT_BATCH_12`.

لا تعدل الكود في هذه الجولة؛ Audit + Recommendation فقط.CONTENT_IMPORT_TEMPLATE_CONTRACT_SYNC_12A

إغلاق الفجوة بين "العقد المركزي" و"ملفات Excel الرسمية + فحص Validate" قبل أول دفعة محتوى حقيقية. لا تغيير في محرك الاستيراد ولا في قاعدة البيانات.

## المشكلة المؤكدة (من مراجعة الكود)

- مولّد القوالب `scripts/generate-content-templates.mjs` لا يُخرج `subject_code` في 04/05/06/07، ولا `explanation_code` في 05، ولا `resource_code` في 06، و`resource_url` فيه غير إلزامي — بينما العقد يعتبرها إلزامية ومنطق التنفيذ في القاعدة يقرأها فعلاً.
- `DRY_RUN_CONFIG` داخل `content-import-templates.ts` قائمة يدوية ثانية، ناقصة نفس الأعمدة ⇒ Validate = PASS لملف قد يفشل أو يفقد الهوية عند Execute.
- ترتيب الواجهة `CONTENT_IMPORT_UI_ORDER = [1..6, 9, 7, 8]` مستقل عن `IMPORT_EXECUTION_ORDER` الحقيقي `[1..7, 9, 8]`.
- مجلد قديم `public/import-templates/` (12 ملفاً) ما زال معروضاً في لوحة الاستيراد عبر `src/lib/import-template-catalog.ts` بجانب الحزمة المعتمدة `public/content-import-templates/`.
- العقد ما زال يصف `assessment_code` و`explanation_code` و`resource_code` كـ `planned_unique` ويشير إلى `migrations-pending`، بينما الأعمدة مطبّقة فعلاً على القاعدة (تم التحقق).

## ما سيتم تنفيذه

### 1. مصدر واحد لأعمدة القوالب

- اشتقاق `requiredColumns` و`knownColumns` لكل قالب من `IMPORT_ENTITY_CONTRACTS[key].fields` بدل القوائم اليدوية.
- إبقاء `infoWarnings` و`duplicateKeyColumn`/`compositeDuplicateKeys` مشتقّة من `naturalKey` في العقد.
- الإبقاء على واجهة `getContentImportDryRunConfig` كما هي حتى لا تتأثر المكونات.

### 2. مولّد القوالب مطابق للعقد

- إضافة `subject_code` (إلزامي) إلى 04، 05، 06، 07.
- إضافة `explanation_code` (إلزامي) إلى 05، و`resource_code` (إلزامي) + جعل `resource_url` إلزامياً في 06.
- مراجعة 01–03 و08–09 عموداً بعمود مقابل العقد، وتحديث صفوف الأمثلة والملاحظات العربية.
- إعادة توليد ملفات `public/content-import-templates/01..09`.

### 3. ترتيب رسمي واحد

- حذف `CONTENT_IMPORT_UI_ORDER` واشتقاق ترتيب العرض من `IMPORT_EXECUTION_ORDER`.
- تحديث `CONTENT_IMPORT_WORKFLOW_ORDER` إلى: `01 → 02 → 03 → 04 → 05 → 06 → 07 → 09 → (Review/Publish) → 08`، مع نص واضح في الواجهة بأن 08 لا يعمل قبل نشر أسئلة 09.

### 4. إغلاق ازدواج القوالب القديمة

- Audit لكل مراجع `public/import-templates/` و`import-template-catalog.ts`.
- إزالة الحزمة القديمة من لوحة الاستيراد (لا عرض ولا تنزيل)، ووسمها Deprecated في README مع الإبقاء على الملفات فقط كأرشيف غير معروض.

### 5. تحديث توصيف العقد ليطابق القاعدة

- تحويل `planned_unique` إلى `db_unique` لـ `explanations` و`resources` و`assessments` بأسماء القيود المطبّقة فعلياً بعد التحقق منها من القاعدة، وإزالة إشارات `migrations-pending`.
- تحديث قوائم `gaps` المغلقة و`IMPORT_GAP_RESOLUTIONS` لتعكس حالة "applied".

### 6. اختبارات حارسة جديدة

- أعمدة كل قالب مولَّد == أعمدة العقد (قراءة الـ xlsx فعلياً).
- `requiredColumns` في Dry-run == الحقول الإلزامية في العقد (parity كامل).
- ترتيب الواجهة == `IMPORT_EXECUTION_ORDER`.
- وجود هويات 04–07 الإلزامية (`subject_code`, `explanation_code`, `resource_code`, `assessment_code`).
- صف المثال في كل قالب رسمي يمر في Validate بنجاح.
- لا وجود لأي مرجع للحزمة القديمة داخل لوحة الإدارة.

## ملاحظات تقنية

- لا Migration في هذه المرحلة؛ التغيير كله في `src/lib/content-import/`, `src/lib/import/import-contract.ts`, `src/lib/import-template-catalog.ts`, `src/routes/_authenticated/admin.import.tsx`, `scripts/generate-content-templates.mjs`, وملفات الاختبارات.
