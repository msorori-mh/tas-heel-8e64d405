# S3.2 — Encrypted transactional offline state

Status: **source and contract implementation; physical Android migration HOLD**

The Android student app now routes the OFFLINE-01 state snapshot through an
app-private SQLite database instead of writing the live snapshot as plaintext
JSON. The payload is encrypted with AES-256-class platform AES/GCM using a
non-exportable key generated inside Android Keystore. Every replacement occurs
inside one SQLite transaction with WAL enabled.

## Upgrade behavior

- On first read, an existing `foundation-v1.json` or verified backup is loaded.
- The snapshot is validated, encrypted, committed, decrypted, and compared.
- Only after successful read-back are both legacy plaintext files removed.
- A failed migration leaves the legacy source available for the next attempt.
- All Java cold-start reads and assessment writes use the same encrypted store.

## Security boundaries

- The JavaScript bridge accepts only the validated snapshot object; it accepts
  no database path, key, SQL, owner override, or ciphertext.
- The AES key never leaves Android Keystore.
- IVs are randomized for every write and authenticated with a 128-bit GCM tag.
- Android backup remains disabled so ciphertext cannot be restored without its
  device-bound key.
- This protects metadata, learning notes, and the outbox. Downloaded content
  artifacts require a later encryption-at-rest batch.

## Remaining device gate

Install an upgrade build over an existing OFFLINE-01 build, then verify in
airplane mode: migration, cold start, lesson listing, answer persistence,
process death, relaunch, and later sync. Inspect app-private storage to confirm
the legacy JSON files are absent and the SQLite payload is not plaintext.
