# تمكين الطالب — بوابة السعة والاستقلال التشغيلي

## القرار المعماري

لا يُعاد بناء المنتج من الصفر ولا تُدار PostgreSQL ذاتيًا قبل وجود فريق تشغيل مناوب.
يبقى Supabase المُدار هو طبقة البيانات، بينما تصبح الملكية والتشغيل والمهاجرات وCI/CD
تحت حسابات المؤسسة مباشرة. Lovable أداة اختيارية للتطوير المرئي، وليس مسار تشغيل وحيدًا.

## مقياس السعة الصحيح

عدد التنزيلات ليس حملًا متزامنًا. التخطيط يعتمد على DAU، ذروة المستخدمين المتزامنين،
عدد الطلبات لكل جلسة، حجم الوسائط، ونسبة العمل دون اتصال.

| السيناريو | التزامن | الطلبات | بوابة النجاح                            |
| --------- | ------: | ------: | --------------------------------------- |
| Smoke     |       1 |      20 | أخطاء ≤1%، P95 ≤1.2s، P99 ≤2.5s         |
| Baseline  |       5 |     200 | الحدود نفسها                            |
| Steady    |      25 |   1,000 | الحدود نفسها                            |
| Spike     |     100 |   2,000 | الحدود نفسها والتعافي دون أخطاء متراكمة |

## التشغيل الآمن

```bash
LOAD_TARGET_URL=https://<staging-ref>.supabase.co \
LOAD_PUBLISHABLE_KEY=<publishable-key> \
LOAD_REPORT_PATH=artifacts/capacity.json \
npm run test:load:staging
```

المشغل يرفض نطاق الإنتاج افتراضيًا. لا تُحفظ مفاتيح أو رموز جلسات في المستودع.
السيناريو الافتراضي يقيس كتالوج الزائر العام (`grades` و`subjects` و`units`) فقط.
تُختبر المسارات المحمية، ومنها `lessons`، في سيناريو طالب مصادق مستقل حتى لا يُحسب
رفض `401` الصحيح كفشل سعة. لا يُشغّل السيناريو المصادق دون حسابات `TEST_ONLY` معزولة.

## خارطة الاستقلال عن Lovable

1. **الملكية:** GitHub وSupabase وDNS وحساب Play Console تحت المؤسسة مع MFA ومالكين اثنين.
2. **التسليم:** مهاجرات مرقمة، staging دائم، CI، نسخة احتياطية واختبار استعادة.
3. **الرصد:** أخطاء الواجهة، زمن RPC، CPU/RAM/IO، الاتصالات، Auth، Storage والتكلفة.
4. **Offline‑First:** قاعدة محلية للمحتوى، manifest بإصدارات وبصمات، outbox للكتابات،
   مزامنة قابلة للإعادة، حل تعارض معلن، وعدم اعتماد الدرس المحمّل على الشبكة.
5. **العميل الأصلي:** لا يبدأ Flutter إلا إذا أثبتت القياسات أن تجربة Capacitor لا تحقق
   احتياجات الأداء/التخزين/الخلفية. عندها يُبنى تدريجيًا فوق API وقاعدة البيانات نفسها.

## بوابات الإطلاق

- اختبار حمل staging ناجح مرتين متتاليتين.
- اختبار انقطاع/استعادة الشبكة وإعادة المحاولة دون ازدواج بيانات.
- RLS وAdvisors بلا ثغرة حرجة.
- نسخ احتياطي وPITR وخطة استعادة مجرّبة.
- تنبيهات قبل بلوغ 60% و80% من موارد Compute والاتصالات والتخزين.
- اختبار إطلاق تدريجي 5% ثم 25% ثم 100% مع إمكانية إيقاف الإصدار.

اختبار HTTP من عامل التنفيذ المحلي غير صالح لاعتماد السعة: طلب منفرد أعاد `200`،
لكن زمن أول بايت كان 10.15 ثانية، بينما اتصال PostgreSQL الإداري المباشر كان طبيعيًا.
الجولة الآلية توقفت مغلقًا في Smoke ولم ترفع الحمل. يجب إعادة الاختبار من GitHub Actions
أو عامل في منطقة قريبة من `ap-south-1`، مرتين متتاليتين، قبل اعتماد أرقام التزامن.

لقطة Advisors الحالية تحتاج تصنيفًا قبل الإطلاق: 267 تحذير أمن و209 تحذيرات أداء.
هذه أعداد نتائج المدقق وليست كلها ثغرات فعلية؛ خصوصًا دوال `SECURITY DEFINER` التي قد
تحتوي تحققًا داخليًا صحيحًا. يمنع الإصلاح الجماعي، وتراجع حسب قابلية الوصول ومسار الاستخدام.

بدأ القياس الخارجي من GitHub Actions، وأثبتت الجولة الأولى أن كتالوج الزائر يعمل ضمن
حدود الزمن، وأن `lessons` محمي ويرفض الزائر بـ`401`. لا تُعتمد السعة حتى تنجح جولتان
كاملتان للسيناريو العام، ويبقى سيناريو الطالب المصادق `HOLD` حتى تتوفر حسابات
`TEST_ONLY` معزولة.
