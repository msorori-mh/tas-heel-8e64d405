## What this proves and excludes

Independent authenticated TEST_ONLY sessions exercised scoped profile/catalog reads,
lesson visibility, durable progress writes, idempotent replay, cross-account progress
denial, and ministerial creation, one text answer, submission and readback. All 100
accounts had submitted exam records in the database after the passing 100 stage.
The final runner additionally requires a completed journey for every VU and checks
denial against another pre-existing profile (not just potentially absent progress).
A five-user functional check of those additions completed for every account with
112 successful requests, including five profile denials, and no journey errors.
Its local network latency gate was HOLD; it is not external performance evidence.

This is a repeated full-journey stress profile with randomized two-second think time,
one Grade 12 subject and one 13-question model, answering one question per attempt.
It is not a measured mix of real student behavior. The highest passing sampled
stage is 100, not a universal maximum student capacity. No one-hour soak, distributed
10k run, refresh storm, Google OAuth, APK/browser rendering or content-byte/CDN test
has passed under this program.

## Diagnosis and next gate

During sampling the database had 23 connections against a configured maximum of 60,
with no observed lock waits. This snapshot does not prove absence of short spikes.
Profile SELECTs in cumulative PostgreSQL statistics averaged 0.09–0.17 ms, while
their HTTP requests timed out under load. Queueing, gateway/pool behavior and shared
resource contention therefore need direct metrics before attributing the problem
to the profile SQL or increasing connection limits.

The performance RPC's cumulative mean rose to about 106 ms and its recorded maximum
was 1,887 ms. A separate cold diagnostic initially took 2,050 ms versus 43 ms with
JIT disabled, but repeated on/off comparisons were 26–53 ms with identical results.
That did not establish a repeatable JIT cause. No global or function JIT setting was
changed, and no speculative index or query rewrite was deployed.

CAP-02 remains HOLD at 500. Next: obtain CPU, memory, I/O, gateway/pool wait and Auth
metrics around a controlled repeat, identify the limiting resource, apply an isolated
fix or measured compute change, then rerun the same gate. Raising timeout or relaxing
latency/error thresholds is not remediation.

CAP-03 is also HOLD: the connector exposes staging only; a direct read of production
project `zbdhxyuulyovihjgeqbn` was denied by the provider. Hosting quotas and production
resource parity are not verified. User authorization is already present; missing
provider access/telemetry is the remaining capability requirement. No paid upgrade
was made. Distributed/session-refresh/soak/CDN/alert deployment work remains gated
behind these findings; it is not marked complete.

## Delivered application change and cleanup

The application change spreads offline retry/reconnect traffic and coalesces duplicate
signals, retaining durable mutation IDs. This reduces synchronized reconnection pressure;
it is not claimed to resolve the 500-user API failure. It requires no production migration
and can be reverted independently. Fifteen targeted offline tests and nine load-runner
contract tests passed; CI verifies build and maintained suites separately.

After the external job stopped, cleanup used a frozen 500-ID/email manifest with matching
TEST_ONLY/run metadata. It revoked test sessions and deleted test users with normal FK
cascades. Transaction checks verified no test profiles, progress, sessions, exams or
offline mutation rows remained, and all 33 retained Auth-user fingerprints were unchanged.
The retained-user fingerprint check covers the cleanup transaction, not a historical
full-database fingerprint from before test setup. Final run-key mutation count: zero.
